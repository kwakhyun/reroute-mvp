# 성능과 대용량 입력 검증

2026-09-05 로컬 검토에서 확인한 문제와 개선 내용입니다. 운영 트래픽이나 실제 사용자의 LCP, INP, CLS를 측정한 결과는 아닙니다.

## 매칭 계산

자산 그룹 16개, 그룹마다 후보 2개인 65,536개 조합을 사용했습니다. 후보는 동일 수량을 인수하며 두 날짜 중 하나를 사용합니다. Node.js 22.21.0에서 DB와 네트워크 없이 실제 엔진을 3회 실행했습니다.

| 상태 | 1회 | 2회 | 3회 |
| --- | --- | --- | --- |
| 개선 전 | 1,502ms, 시간 초과 | 1,501ms, 시간 초과 | 1,501ms, 시간 초과 |
| 개선 후 | 324.14ms, 완료 | 229.14ms, 완료 | 127.31ms, 완료 |

개선 후에도 합산 효과 32, 매각 대금 16인 같은 최적 결과를 반환합니다. 전수 탐색의 평가 기준과 ID 동률 처리 순서를 유지하고, 날짜 키 변환과 합계 계산의 반복만 줄였습니다. 40개의 다른 입력 묶음에서도 독립적인 전체 조합 평가와 같은 결과인지 테스트합니다. 실행 시 시스템 부하와 JIT 준비 상태에 따라 시간이 달라집니다. 개선 전에는 완료되지 않았으므로 완료 시간의 배수 비교를 주장하지 않습니다.

재현 명령:

```bash
node --import tsx scripts/benchmark-matching.ts
```

100,000조합 상한과 1.5초 동기 실행 제한은 그대로입니다. 더 큰 입력이나 여러 동시 요청에 대한 Worker/큐 분리는 운영 측정 후 결정합니다.

## 입찰 저장과 조회

- 인수처를 한 번에 저장하면 5,000개 × 9개 필드만으로도 45,000개 SQL 바인딩이 필요했습니다. 현재는 인수처와 입찰을 각 50행 단위로 나눕니다.
- 기존 인수처는 배치 UPSERT로 갱신합니다. 인수처별로 UPDATE를 반복하지 않습니다.
- 실제 서버 액션 테스트에서 5,000행 저장, 신규/기존 인수처 혼합 교체, 저장 중 DB 트리거 실패 후 원상 복구를 확인합니다. 이 테스트만 커버리지 계측의 추가 비용을 고려해 실행 제한을 90초로 둡니다. 앱 요청이나 계산의 제한을 늘린 것은 아닙니다.
- 화면은 서버에서 50행씩 조회합니다. 자산/배분안 포함 필터와 페이지 이동은 전체 CSV 내보내기 범위를 줄이지 않습니다.
- 자산 화면은 자산만, 정산 화면은 배분안 요약만 조회합니다. 수거는 배분 상세를 조회하고 자산 전체 목록과 입찰 개수 조회는 생략합니다.

## 화면과 스타일

- 기능별 스타일 분리 당시 앱 전역 CSS는 4,018행에서 354행으로 줄이고 기능별 CSS Modules로 분리했습니다. 이는 책임 분리를 나타내는 소스 행 수이며 전송량 감소율을 뜻하지 않습니다.
- 공개 소개의 빌드 HTML이 불러오는 CSS에 사이드바와 입찰 표 스타일이 포함되지 않는 것을 확인했습니다. 공통 폰트와 기본 스타일은 계속 공유합니다.
- 대표 이미지는 Next Image의 반응형 변환과 `preload`를 사용합니다. 글자 선명도와 실제 이미지 로딩은 브라우저 검증에 포함합니다.
- 표는 ResizeObserver로 실제 넘침을 확인해 스크롤 안내와 키보드 포커스를 제공합니다. 중간 화면 폭에서는 두 배분 표를 세로로 배치합니다.
